# P1.01 — Logged VMApple Baseline Harness

Project version: **`0.2.0.0.0.0`**

Parent: **Part 01 — VMApple Baseline and Host-Dependency Map**

Status: **Started**

## Objective

P1.01 is the first small implementation objective inside Part 01.

Its job is to establish one rule that every later experiment can depend on:

> AppleSilicon must never perform a meaningful emulator, probe, compatibility, or boot run without leaving a persistent diagnostic `.log` file.

P1.01 does **not** attempt to boot macOS on generic ARM64 hardware yet.

It creates the execution and evidence layer that will let later objectives answer exactly where a boot succeeded, where it failed, and what configuration produced the result.

## Why this comes first

This project will eventually contain many separate compatibility parts. A single boot may pass through firmware, CPU initialization, memory setup, interrupts, timers, VMApple configuration, block devices, XNU, IOKit, userspace, and graphics.

Without persistent logs, an early failure can become impossible to distinguish from a later failure.

The project therefore treats logging as part of the machine design rather than an optional debugging feature.

The maintainer will not manually test every intermediate update. This makes reproducible logs and automated/development-side checks even more important: intermediate work must be understandable from captured evidence instead of depending on repeated manual end-user testing.

## P1.01 requirements

### P1.01.R1 — One log per run

Every meaningful executable run must create one new file using the default naming scheme:

```text
logs/AppleSilicon-YYYYMMDD-HHMMSS.log
```

If multiple runs occur within one second, the launcher may append a process ID or sequence number to avoid overwriting a previous log.

### P1.01.R2 — Never overwrite an earlier run silently

Logs are append-by-run artifacts. A new execution must create a new file unless a developer explicitly requests continuation of an existing trace.

### P1.01.R3 — Minimum metadata

When available, the beginning of the log records:

```text
AppleSilicon version
UTC timestamp
host operating system
host architecture
selected accelerator
selected CPU model
selected machine model
upstream revision
execution command/configuration summary
```

The end of the log records:

```text
exit code
shutdown reason, if known
final boot stage, if known
fatal error or panic, if known
```

### P1.01.R4 — Capture both stdout and stderr

A failure printed only to `stderr` is still a failure. Both standard output and standard error must enter the same diagnostic run log unless a later subsystem has a documented reason to split them.

### P1.01.R5 — Do not log secrets

Logs must not intentionally contain:

```text
Apple account credentials
passwords
private keys
cryptographic tickets
personal authentication tokens
machine secrets
private firmware material
```

Paths and non-secret configuration may be logged when useful. Future launchers that accept sensitive fields must redact them before writing the command/configuration summary.

### P1.01.R6 — Logging survives failure

The log must still be created when the launched command exits unsuccessfully.

An emulator crash or unsupported-instruction error is not a reason to lose the log; it is exactly when the log is most useful.

## First implementation

The first generic implementation is:

```text
src/tools/run-logged.sh
```

It is a development wrapper around any future AppleSilicon command.

Conceptually:

```text
command
   ↓
run-logged.sh
   ├── creates timestamped .log
   ├── records run metadata
   ├── captures stdout
   ├── captures stderr
   ├── records exit status
   └── returns the original command's exit status
```

This wrapper is deliberately generic. Later launchers can replace it with richer structured logging, but they must preserve the one-log-per-run rule.

## P1.01 development-only example

A developer can eventually invoke a command through the wrapper as:

```bash
src/tools/run-logged.sh ./src/upstream/inferno/build/qemu-system-aarch64 --version
```

or, once VMApple probe configurations exist:

```bash
src/tools/run-logged.sh ./src/upstream/inferno/build/qemu-system-aarch64 \
  -accel tcg \
  -cpu max \
  -M vmapple
```

The second command is only an example of the future probe shape and is not claimed to boot successfully.

## Maintainer testing rule

P1.01 does not create an intermediate manual testing requirement.

The maintainer is not expected to run P1.01, P1.02, individual fixes, hotfixes, or every project update. Manual maintainer testing is reserved for the finished integration stage.

During development, the repository should rely on source inspection, reproducible build checks, automated tests where possible, and captured emulator/runtime logs generated by the development environment.

## Acceptance criteria

P1.01 is complete when:

1. The repository contains a reusable logged-run wrapper or equivalent launcher infrastructure.
2. A future command launched through that infrastructure always receives a unique `.log` destination.
3. stdout and stderr are both captured.
4. host/version/timestamp information is written before the target command runs.
5. the target command's exit code is written to the log and propagated back to the caller.
6. generated `.log` files are excluded from normal Git commits.
7. Part 01 documentation references this objective.
8. no maintainer/manual intermediate test is required to mark the source change itself complete.
