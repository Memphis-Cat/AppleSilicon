# P1.03 — VMApple Capability & Build-Gate Probe

Project version: **`0.3.0.0.0.0`**

Parent: **Part 01 — VMApple Baseline and Host-Dependency Map**

Status: **Implementation started**

## Objective

P1.03 determines what the pinned Inferno build actually exposes before AppleSilicon changes VMApple or begins Apple CPU compatibility work.

The goal is to answer four questions with evidence:

```text
1. Was the vmapple machine compiled into qemu-system-aarch64?
2. Which accelerators are available in this build?
3. Which AArch64 CPU models are available in this build?
4. What compile-time and machine-level constraints currently prevent the generic path?
```

P1.03 does not boot macOS and does not require Apple guest material.

## Research finding: VMApple is currently gated by HVF

The pinned Inferno revision contains this VMApple Kconfig relationship:

```text
config VMAPPLE
    bool
    depends on ARM
    depends on HVF
```

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/vmapple/Kconfig>

Current upstream QEMU contains the same `depends on HVF` gate:

<https://github.com/qemu/qemu/blob/master/hw/vmapple/Kconfig>

This is a critical distinction.

A successful P1.02 Linux build can produce a valid `qemu-system-aarch64` executable while still containing **no VMApple machine at all**, because Linux does not provide Apple's Hypervisor.framework/HVF accelerator.

Therefore:

```text
qemu-system-aarch64 exists
```

does not imply:

```text
-M vmapple exists
```

P1.03 exists to make that difference explicit and machine-readable before any later objective modifies the gate.

## Research finding: the current default VMApple CPU is `host`

The pinned VMApple machine class currently sets:

```c
mc->default_cpu_type = ARM_CPU_TYPE_NAME("host");
```

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/vmapple/vmapple.c>

The machine also disables guest EL2 and EL3 when those properties exist, uses PSCI through HVC, starts secondary CPUs powered off, and creates a GICv3-based virtual platform.

This means the current VMApple path is not merely an M-series physical machine model. It is a virtual Mac platform whose CPU side is presently designed around a host CPU exposed through the virtualization path.

## Research finding: QEMU itself supports a generic TCG ARM path

QEMU documents TCG as its software CPU emulator and supports AArch64 system emulation. The `max` AArch64 CPU model is intended to expose the broadest CPU feature set available in TCG.

Primary sources:

<https://www.qemu.org/docs/master/about/emulation.html>

<https://www.qemu.org/docs/master/system/arm/emulation.html>

This does **not** prove that `-cpu max` can run macOS. It proves only that a software-emulated AArch64 CPU path exists for us to investigate once VMApple can be compiled independently of HVF.

## Research finding: current documented VMApple usage is HVF/Apple-Silicon-specific

QEMU's current VMApple documentation still lists an Apple Silicon host and macOS host as prerequisites and demonstrates the machine with:

```text
-accel hvf
-M vmapple
```

Primary source:

<https://www.qemu.org/docs/master/system/arm/vmapple.html>

That documented restriction and the Kconfig gate are separate pieces of evidence:

```text
Kconfig gate     -> can the machine be built?
runtime support  -> can the built machine actually execute correctly?
```

P1.03 inventories the first boundary without pretending it solves the second.

## P1.03 requirements

### P1.03.R1 — Preserve the exact upstream reference

The probe must record and validate the pinned Inferno revision:

```text
cc4302a99167abec69b714cfd00c38caece7e7de
```

If the observed source revision differs, the result is not a P1.03 reference result.

### P1.03.R2 — Inspect the source build gate

The probe records whether the pinned source contains:

```text
depends on ARM
depends on HVF
```

for `CONFIG_VMAPPLE`.

This is source evidence, not a guess based on the host operating system.

### P1.03.R3 — Inspect the default VMApple CPU contract

The probe records whether the machine source still declares:

```text
ARM_CPU_TYPE_NAME("host")
```

as the default CPU type.

If this changes in a later upstream revision, the probe must make that visible instead of continuing to assume `host`.

### P1.03.R4 — Verify machine presence in the built emulator

When a P1.02-built emulator is available, the probe runs the equivalent of:

```bash
qemu-system-aarch64 -machine help
```

and determines whether `vmapple` is present.

Classification:

```text
VMAPPLE_PRESENT
VMAPPLE_NOT_COMPILED
```

`VMAPPLE_NOT_COMPILED` is a valid P1.03 finding, not a generic script failure.

### P1.03.R5 — Inventory accelerators

The probe records:

```bash
qemu-system-aarch64 -accel help
```

The output is preserved in the P1.03 `.log`.

Important accelerator classes for later work include:

```text
hvf
kvm
tcg
```

Presence is recorded exactly as the binary reports it.

### P1.03.R6 — Inventory AArch64 CPU models

The probe records:

```bash
qemu-system-aarch64 -cpu help
```

This establishes what the compiled emulator can actually select instead of assuming that a CPU model exists because another QEMU build supports it.

Particular later interest includes:

```text
host
max
named ARM CPU models
```

### P1.03.R7 — Query VMApple properties when available

If `vmapple` is compiled, the probe attempts a non-booting machine-property query:

```bash
qemu-system-aarch64 -M vmapple,help
```

Failure of the help query is recorded but does not trigger any guest boot attempt.

### P1.03.R8 — No firmware or macOS required

P1.03 must not require:

```text
AVPBooter
AUX image
macOS disk image
IPSW
Apple account
machine identity
Apple firmware
```

The objective concerns emulator capabilities only.

### P1.03.R9 — One persistent log

P1.03 inherits P1.01.

Every capability probe writes a unique `.log` under:

```text
.logs/
```

The log includes source revision, source-gate state, VMApple CPU-default state, QEMU version, machine list, accelerator list, CPU list, VMApple property output when available, final classification, final stage, and exit code.

### P1.03.R10 — No manual maintainer testing

The owner is not required to run P1.03 now.

The harness is implemented and source-reviewed during development. Runtime execution remains deferred under the project-wide final-testing rule.

## Initial implementation

P1.03 introduces:

```text
.src/.tools/probe-vmapple.sh
.src/.configs/vmapple-probe.env.example
```

The probe has two conceptual layers:

```text
source inspection
    ↓
CONFIG_VMAPPLE gate
VMApple default CPU
pinned revision

binary inspection
    ↓
-machine help
-accel help
-cpu help
-M vmapple,help
```

The two layers are deliberately kept separate.

If the source says VMApple is gated by HVF and a Linux binary does not contain `vmapple`, that is a clean, understood result.

## Classification model

P1.03 uses explicit classifications instead of vague success/failure wording.

### `SOURCE_ONLY`

The pinned source was successfully inspected but no P1.02 emulator binary was available.

This is useful for development/source review but is not a runtime capability result.

### `VMAPPLE_NOT_COMPILED`

The emulator exists, but `-machine help` does not list `vmapple`.

With the current source, the first suspected reason is the HVF Kconfig dependency, but the log must preserve enough evidence to verify that rather than hard-coding the conclusion.

### `VMAPPLE_PRESENT`

The emulator lists `vmapple`.

This does not mean it can boot macOS or operate with TCG/KVM. It only means the machine model is present in that binary.

## Success condition

P1.03 implementation is complete when the repository can deterministically produce the following evidence without booting a guest:

```text
pinned source revision
VMAPPLE ARM gate: yes/no
VMAPPLE HVF gate: yes/no
VMApple default CPU = host: yes/no
qemu-system-aarch64 version
vmapple machine present: yes/no
available accelerators
available CPU models
vmapple property/help result, if present
final classification
persistent log
```

Runtime capability results remain unclaimed until the project is eventually tested.

## P1.04 boundary

P1.03 is intentionally observational.

P1.04 may begin changing the upstream behavior only after the current gate is documented.

Based on the current evidence, the likely next objective is:

```text
P1.04 — Decouple VMApple Build From HVF
```

That objective would aim to make the VMApple machine **compile** in an AArch64 TCG-capable build without pretending that removing a Kconfig dependency alone makes macOS boot.

The distinction is important:

```text
compile VMApple without HVF
        !=
run VMApple correctly without HVF
        !=
run modern macOS on generic ARM64
```

Each is a separate objective.
