# P1.05 — Decouple VMApple Machine Realization From Apple PVG

Project version: **`0.5.0.0.0.0`**

Parent: **Part 01 — VMApple Baseline and Host-Dependency Map**

Status: **Implementation started**

## Objective

P1.05 makes the VMApple machine implementation capable of continuing machine construction when the Darwin-only Apple ParavirtualizedGraphics MMIO device is not compiled into QEMU.

This objective does **not** emulate an Apple GPU, does not provide a fake framebuffer, and does not claim macOS graphics support.

Its purpose is narrower:

> The absence of `apple-gfx-mmio` must no longer abort VMApple machine realization before the project can reach the CPU and early-platform experiments that Part 01 exists to perform.

The existing Apple PVG path must remain unchanged when the device is available.

Runtime machine-instantiation testing remains deferred under the project-wide final-testing rule.

## Research result

The pinned Inferno revision remains:

```text
ChefKissInc/Inferno
cc4302a99167abec69b714cfd00c38caece7e7de
```

VMApple currently constructs graphics unconditionally:

```c
gfx = SYS_BUS_DEVICE(qdev_new("apple-gfx-mmio"));
```

and then maps two MMIO regions and two interrupt lines.

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/vmapple/vmapple.c>

The corresponding `apple-gfx-mmio` implementation is Objective-C code backed by Apple's `ParavirtualizedGraphics.framework`. It imports that framework directly and implements both the graphics MMIO device and IOSurface-host communication path.

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/display/apple-gfx-mmio.m>

Inferno's Meson configuration only discovers the Apple ParavirtualizedGraphics and Metal frameworks on Darwin. The display source is added only when the PVG dependency and `CONFIG_MAC_PVG_MMIO` are both available.

Primary sources:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/meson.build>

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/display/meson.build>

Therefore, after P1.04 removes the HVF build gate, a host-neutral build may contain VMApple while not containing the QOM type named:

```text
apple-gfx-mmio
```

Calling `qdev_new()` for a missing QOM type is the wrong contract for this stage.

## QEMU-provided solution primitive

QEMU already provides two device-construction paths:

```c
qdev_new(name)
qdev_try_new(name)
```

`qdev_try_new()` performs module-aware class lookup and returns `NULL` if the device type does not exist instead of assuming it is present.

Current QEMU source:

<https://github.com/qemu/qemu/blob/master/hw/core/qdev.c>

P1.05 uses that existing mechanism rather than inventing a new device registry or compile-time host test.

This is preferable to checking `#ifdef __APPLE__`, `CONFIG_HVF`, or the host operating system because the real question is not:

```text
Is the host macOS?
```

It is:

```text
Does this QEMU binary contain a usable apple-gfx-mmio QOM device type?
```

That distinction matters for future builds, modules, and alternative implementations.

## P1.05 behavior

After P1.05, `create_gfx()` performs the equivalent of:

```c
DeviceState *gfx_dev = qdev_try_new("apple-gfx-mmio");

if (!gfx_dev) {
    warn_report("VMApple: apple-gfx-mmio unavailable; continuing without Apple PVG");
    return;
}
```

When the device exists:

```text
apple-gfx-mmio found
        ↓
existing MMIO mappings preserved
existing IRQ wiring preserved
existing Apple PVG realization preserved
```

When it does not exist:

```text
apple-gfx-mmio absent
        ↓
warning recorded
no fake GPU created
no PVG MMIO region created
VMApple machine construction continues
```

The APV GFX and IOSFC address ranges remain part of the documented VMApple memory map, but no replacement device is silently installed at those addresses.

An eventual guest access to an unimplemented graphics range is a later observable compatibility event, not something P1.05 should hide with guessed behavior.

## Why no fake framebuffer is added

A dummy graphics device could make machine construction appear more complete while providing behavior that macOS never actually expects.

That would violate the project rule that compatibility behavior should be implemented from evidence rather than appearance.

P1.05 therefore does **not** add:

```text
fake AGX
fake PVG registers
fake IOSurface responses
fake Metal support
fake framebuffer responses
```

If early Apple boot requires a minimal graphics contract, that requirement must be discovered and implemented as its own objective with traceable evidence.

## P1.05 implementation files

P1.05 introduces:

```text
.src/.patches/0002-vmapple-optional-apple-pvg.patch
.src/.tools/prepare-p1.05.sh
```

The preparation harness must:

1. validate the exact pinned Inferno revision,
2. refuse a dirty tracked baseline,
3. verify P1.04 and P1.05 patches both apply in order,
4. create a disposable source tree under `.build/p1.05/`,
5. initialize Inferno's nested submodules,
6. apply P1.04,
7. apply P1.05,
8. verify `qdev_try_new("apple-gfx-mmio")` is used,
9. verify the unconditional `qdev_new("apple-gfx-mmio")` call is gone,
10. verify existing MMIO and IRQ wiring is still present,
11. verify VMApple still calls `create_gfx()`,
12. verify the VMApple CPU default is still `host`,
13. preserve the complete preparation result in a unique `.log` file.

## Success condition

P1.05 implementation is complete when the source patch deterministically provides this contract:

```text
PVG device available
    -> preserve existing VMApple graphics path

PVG device unavailable
    -> record warning
    -> skip PVG device creation
    -> continue VMApple machine construction
```

while also preserving:

```text
P1.04 non-HVF build gate
VMApple memory map
PVG MMIO/IRQ wiring when PVG exists
host CPU default
pinned upstream revision
persistent logging
```

Runtime machine construction and guest behavior remain unclaimed until final project testing.

## P1.06 boundary

Once VMApple can be compiled without HVF and can construct its device graph without requiring Apple PVG, the next first-order blocker becomes the CPU selection contract.

The current VMApple machine still defaults to:

```c
mc->default_cpu_type = ARM_CPU_TYPE_NAME("host");
```

The next objective is therefore expected to be:

```text
P1.06 — Explicit Non-Host VMApple CPU Selection
```

P1.06 should make a controlled TCG-oriented CPU selection possible without yet pretending that a generic QEMU ARM CPU satisfies macOS' Apple-specific CPU expectations.
