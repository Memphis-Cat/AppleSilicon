# P1.02 — Reproducible Inferno Build Baseline

Project version: **`0.2.0.0.0.0`**

Parent: **Part 01 — VMApple Baseline and Host-Dependency Map**

Status: **Implementation complete — runtime build intentionally deferred**

## Objective

P1.02 establishes a reproducible build baseline for the exact pinned ChefKiss Inferno revision used by AppleSilicon.

The purpose is not to boot macOS yet. Before changing VMApple, CPU behavior, or Apple-specific devices, AppleSilicon needs to know that the upstream emulator can be obtained, configured, compiled, identified, and logged in a repeatable way.

A future compatibility failure must be distinguishable from a broken or inconsistent build environment.

## Implementation state

The P1.02 source implementation now exists in the repository:

```text
.src/.tools/build-inferno.sh
.src/.configs/inferno-build.env.example
```

The build harness is executable and implements revision validation, toolchain preflight, recursive Inferno submodule initialization, dependency reporting, a clean out-of-tree build directory, host-specific configure profiles, compilation, `qemu-system-aarch64` artifact verification, version reporting, failure propagation, and persistent `.log` output.

The project owner is not being asked to execute this objective. Runtime build validation remains intentionally deferred under the project testing rule.

## Research basis

The pinned upstream revision is:

```text
ChefKissInc/Inferno
cc4302a99167abec69b714cfd00c38caece7e7de
```

Inferno's build workflow at this revision provides three useful reference environments:

```text
Ubuntu / Linux
macOS 26 / Apple Silicon
macOS 26 / Intel
```

Its CI performs an out-of-tree build and configures the QEMU-derived source with `aarch64-softmmu` and `x86_64-softmmu` targets before invoking `make`.

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/.github/workflows/build.yaml>

QEMU's current build-system documentation independently confirms that the intended build pattern is an out-of-tree build directory followed by `configure` and `make`, while Meson and Ninja implement much of the underlying build graph.

Primary source:

<https://www.qemu.org/docs/master/devel/build-system>

## P1.02 requirements

### P1.02.R1 — Exact upstream revision

The build system must refuse to silently treat an arbitrary Inferno checkout as the reference baseline.

The expected revision is:

```text
cc4302a99167abec69b714cfd00c38caece7e7de
```

The revision must be recorded in the build log.

### P1.02.R2 — Recursive source initialization

The baseline must account for Inferno's own Git submodules.

A clean AppleSilicon checkout therefore uses recursive submodule initialization.

The project must not copy Inferno source files into AppleSilicon and lose upstream history or licensing information.

### P1.02.R3 — Out-of-tree build

Build artifacts must not be mixed with the pinned source tree.

The baseline build directory is project-generated and disposable.

Conceptually:

```text
.src/.upstream/.inferno     source
.build/inferno              generated build tree
.logs                       generated logs
```

`.build` and `.logs` are generated working directories and are not source directories.

### P1.02.R4 — AArch64 system emulator is mandatory

The build must include:

```text
aarch64-softmmu
```

because AppleSilicon's VMApple work needs `qemu-system-aarch64`.

For baseline parity with Inferno CI, `x86_64-softmmu` may also be enabled, but AppleSilicon must fail P1.02 if `qemu-system-aarch64` is not produced.

### P1.02.R5 — Reference configure profile

The first AppleSilicon baseline profile follows Inferno CI rather than inventing a new feature combination.

Common required intent:

```text
--target-list=aarch64-softmmu,x86_64-softmmu
--disable-guest-agent
--enable-slirp
--enable-lzfse
--enable-nettle
--enable-gnutls
--disable-werror
```

Host-specific options may differ between Linux and macOS and must be logged.

### P1.02.R6 — Dependency discovery is explicit

The baseline must detect required tools before compilation and report missing dependencies clearly.

At minimum the preflight records availability/version information for:

```text
git
python3
make
cc/clang/gcc
pkg-config or pkgconf
meson
ninja
```

Host package dependencies are not assumed to be identical across Linux and macOS.

Inferno's own CI dependency lists are the primary initial reference.

### P1.02.R7 — Every build is logged

P1.02 inherits P1.01.

A build is never considered a baseline build unless its configure and compile output are captured in a persistent `.log` file.

The log must include:

```text
AppleSilicon version
host OS
host architecture
Inferno expected revision
Inferno observed revision
compiler identity
configure command
configure exit code
build command
build exit code
produced qemu-system-aarch64 path
qemu-system-aarch64 --version output, when available
```

### P1.02.R8 — No maintainer manual test required

The project owner is not required to manually test P1.02.

P1.02 is validated through source inspection, deterministic scripts, automated/development-side build checks when an appropriate environment is available, and persistent logs.

Manual maintainer testing remains reserved for final integrated project testing.

### P1.02.R9 — No Apple guest material

P1.02 only builds the emulator.

It must not require or download:

```text
macOS installers
IPSWs
AVPBooter
Apple firmware
machine identifiers
Apple account credentials
keys or tickets
```

Those belong to later controlled boot experiments, not the build baseline.

## Baseline host profiles

### macOS

Inferno CI uses Homebrew packages including build tools and libraries such as libtool, Meson, Ninja, pkgconf, dtc, GLib, GnuTLS, jpeg-turbo, libpng, libslirp, libssh, libusb, lzo, ncurses, nettle, pixman, snappy, vde, zstd, and lzfse.

Its macOS configure invocation additionally selects Cocoa and uses Homebrew include/library paths.

P1.02 does not automatically install Homebrew or modify the host package manager. The build script detects and reports prerequisites; dependency installation remains an explicit environment preparation action.

### Linux

Inferno CI uses Ubuntu and installs the corresponding build toolchain/development libraries. It also builds Nettle 3.10.2 from source in CI before configuring Inferno.

The Linux baseline therefore records Nettle availability/version and does not pretend every distribution exposes identical package names.

## Success condition

P1.02's source implementation is complete when the repository contains a deterministic baseline build harness that can:

1. identify the pinned Inferno checkout,
2. validate its revision,
3. preflight the build environment,
4. configure an out-of-tree build including `aarch64-softmmu`,
5. invoke the build,
6. verify `qemu-system-aarch64` exists,
7. record the resulting emulator version,
8. preserve the complete run in a `.log`, and
9. return a non-zero status on any failed stage.

Those behaviors are implemented in the harness. Actual execution of the full build is deferred until project testing is permitted by the project testing rule.

## What P1.02 does not prove

P1.02 does not yet prove that a runtime build has succeeded on the maintainer's machine, because intermediate manual testing is intentionally deferred.

Even when the build is later executed successfully, that will still not prove:

```text
VMApple boots
macOS boots
TCG can replace an Apple host CPU
Apple CPU registers are implemented
GPU acceleration works
future macOS compatibility works
```

Those remain later objectives.

## Next objective boundary

P1.03 should begin from the resulting emulator contract rather than changing Apple CPU behavior blindly.

Its likely responsibility is to inventory and probe `qemu-system-aarch64` VMApple machine constraints: machine registration, allowed accelerators, default CPU selection, host-only assumptions, firmware inputs, and the earliest constraints that must change before a generic ARM/TCG path can be attempted.
