# P3.05 — PCIe, Peripheral, Crypto and Graphics Contract

Project version: **`3.4.0.0.0.0`**

Status: **Implementation complete — guest/runtime peripheral, AES and graphics validation intentionally deferred**

## Objective

Freeze the remaining non-CPU VMApple peripheral contract owned by P3.05 without replacing working generic QEMU devices, inventing undocumented AES behavior, or substituting a fake graphics device for Apple's host-only paravirtual graphics path.

P3.05 owns the P3.01 components:

- `pcie_gpex`
- `xhci_usb`
- `virtio_network`
- `vmapple_aes`
- `apple_pvg_graphics`

It does not own CPU behavior, configuration identity, GIC/timer/UART/power wiring, BDIF or VMApple storage.

## Result

The source-backed ownership split is:

```text
generic QEMU
├── GPEX PCIe host bridge
├── virtio PCI transport
├── virtio-net-pci
├── qemu-xhci
├── usb-kbd
└── usb-tablet

VMApple-specific
└── Apple AES MMIO device

host-framework dependent
└── apple-gfx-mmio / Apple PVG
```

No new P3.05 Inferno source patch is justified by the available evidence.

The existing P1.05 optional-PVG patch remains part of the platform contract and is preserved unchanged.

## PCIe contract

VMApple uses generic QEMU GPEX infrastructure.

The machine maps:

```text
PCIe ECAM
base  0x40000000
size  0x10000000

PCIe MMIO
base  0x50000000
size  0x1fff0000
```

The GPEX host is configured with:

```text
16 interrupt lines
SPI base  32 / 0x20
SPI last  47 / 0x2f
```

The interrupt arithmetic is therefore:

```text
32 + 16 - 1 = 47
```

P3.05 preserves the generic GPEX implementation. No evidence currently supports replacing it with an Apple physical PCIe controller model.

## Virtio transport and networking

VMApple applies this compatibility default:

```text
disable-legacy=on
```

to the generic virtio PCI transport.

This is part of the VMApple machine contract and must remain enabled.

Configured NIC backends are realized as ordinary:

```text
virtio-net-pci
```

Networking remains an optional reference component rather than a boot requirement.

## XHCI and macOS interrupt compatibility

VMApple creates the generic:

```text
qemu-xhci
```

controller when machine defaults are enabled.

It also applies:

```text
conditional-intr-mapping=on
```

The XHCI implementation defines this policy so interrupter mapping is enabled only when MSI or MSI-X is actually active. When the controller falls back to pin-based PCI interrupts, guest events are forced onto interrupter/event ring 0 instead of being lost on other interrupters.

This behavior exists specifically to accommodate macOS guest-driver behavior when MSI/MSI-X is unavailable.

The XHCI PCI implementation keeps both:

```text
msi=auto
msix=auto
```

as its defaults.

P3.05 therefore treats `conditional-intr-mapping=on` as a compatibility contract, not an incidental implementation detail.

There is no missing P3.05 XHCI patch: the pinned Inferno tree already includes the compatibility behavior.

## Default USB devices

When defaults are enabled, VMApple adds:

```text
usb-kbd
usb-tablet
```

behind the generic XHCI controller.

These remain optional reference peripherals. Their presence is not promoted to an XNU boot requirement.

## AES MMIO contract

VMApple exposes the Apple AES device at two MMIO windows:

```text
AES1
base  0x30220000
size  0x00004000
SPI   18 / 0x12

AES2
base  0x30230000
size  0x00004000
```

The implementation accepts 4- to 8-byte valid accesses while executing 4-byte MMIO operations internally.

P3.05 preserves this geometry without asserting that every undocumented AES register is known.

## AES command contract

The public implementation declares command IDs:

```text
KEY        0x1
IV         0x2
DSB        0x3
SKG        0x4
DATA       0x5
STORE_IV   0x6
WRITE_REG  0x7
FLAG       0x8
```

But the command processor implements only:

```text
KEY
IV
DATA
STORE_IV
FLAG
```

The following remain declared but unimplemented:

```text
DSB
SKG
WRITE_REG
```

P3.05 does not invent semantics for them. Their necessity is:

```text
unknown_requires_runtime_evidence
```

A future runtime trace may promote one of these into an implementation objective, but source declaration alone is insufficient.

## AES cryptographic behavior

The public model supports:

```text
AES-128
AES-192
AES-256

ECB
CBC
```

and performs DMA-backed data movement through QEMU's crypto APIs.

The source also contains builtin-key slots 1, 2 and 3 initialized with trivial public constants.

P3.05 explicitly classifies these as:

```text
public emulator placeholders
not authentic Apple secrets
```

They must not be described, exported or treated as real Apple hardware keys.

## AES reset state

The source-backed reset state is:

```text
status      0x3f80
q_status    2
irq_status  0
irq_enable  0
watermark   0
```

P3.05 freezes those values as reference-emulator behavior, not as proof that every bit's real-hardware semantic meaning is known.

## Apple PVG graphics boundary

The VMApple reference machine creates:

```text
apple-gfx-mmio
```

at:

```text
GFX
base  0x30200000
size  0x00010000
SPI   17

IOSFC
base  0x30210000
size  0x00010000
SPI   16
```

The device implementation directly uses Apple's host frameworks:

```text
ParavirtualizedGraphics.framework
Metal.framework
```

This is therefore a host-framework-dependent path, not a portable software GPU model.

## Existing P1.05 portability policy

P1.05 already changed VMApple graphics construction from unconditional device creation to:

```text
qdev_try_new("apple-gfx-mmio")
```

If the device type is unavailable, the machine warns and continues without PVG.

P3.05 preserves that policy exactly:

```text
real Apple PVG available -> use it
Apple PVG unavailable    -> warn and continue
fake replacement GPU     -> forbidden
```

This keeps non-Darwin TCG work possible without pretending to implement Apple's graphics protocol.

## Modern VMApple graphics status

P3.05 does not claim that current QEMU VMApple graphics supports modern macOS guests.

QEMU 11.1.0 still disables VMApple in the default AArch64 device configuration:

```text
CONFIG_VMAPPLE=n
```

The official VMApple documentation still limits its stated guest support to macOS 12.x, and upstream issue 2913 remains the evidence marker for the macOS 15.4 unusability problem.

This status is tracked as:

```text
unknown_requires_evidence / deferred
```

rather than patched with a guessed graphics implementation.

## No new Inferno patch

P3.05 adds no `0006` patch.

The current reasoning is:

```text
GPEX/virtio/XHCI
    existing generic QEMU behavior + macOS compatibility default
    -> preserve and validate

AES
    existing VMApple-specific partial public model
    -> preserve known behavior; evidence-gate missing commands

Apple PVG
    host-framework dependent + already optionalized by P1.05
    -> preserve optional path; no fake GPU
```

## Implementation

P3.05 adds:

```text
.src/.configs/p3.05-peripheral-contract.json
.src/.tools/platform-peripheral-contract.py
.src/.tools/prepare-p3.05.sh
```

The validator checks:

- source revisions and blob locks;
- PCIe ECAM/MMIO geometry;
- 16-line GPEX IRQ range;
- virtio legacy-mode disablement;
- generic `virtio-net-pci` ownership;
- XHCI MSI/MSI-X and conditional-interrupter behavior;
- default USB HID devices;
- AES MMIO/IRQ/reset contract;
- implemented versus unresolved AES commands;
- public-placeholder classification of builtin AES constants;
- Apple PVG MMIO/IRQ and framework dependency;
- P1.05 optional-PVG patch identity;
- absence of a fake GPU policy;
- modern VMApple graphics remaining unresolved;
- P3.06 as the only next Part 03 objective.

`prepare-p3.05.sh` performs logged deterministic source/contract validation without launching a guest or opening Apple firmware/storage/identity artifacts.

## Runtime state

No real macOS/HVF/TCG guest execution is claimed by P3.05.

Runtime questions deliberately left for integrated evidence include:

- whether the target guest exercises AES DSB/SKG/WRITE_REG commands;
- whether additional AES behavior is required beyond the public implementation;
- whether modern guest versions require a different graphics contract;
- whether optional USB/network devices expose additional guest-specific quirks.
