# P1.07 — TCG VMApple Pre-Boot Probe Harness

Project version: **`0.7.0.0.0.0`**

Parent: **Part 01 — VMApple Baseline and Host-Dependency Map**

Status: **Implementation complete — runtime probe intentionally deferred**

## Objective

P1.07 creates the first complete, reproducible launch harness for a VMApple machine running through TCG with an explicit non-host ARM64 CPU profile.

This objective does not claim that macOS boots, that AVPBooter accepts the selected CPU, or that `max`/`apple-gxf` is Apple-Silicon-compatible.

Its job is to make the first future failure measurable.

The controlled experiment is:

```text
prepared VMApple source
  + P1.04 non-HVF build gate
  + P1.05 optional Apple PVG
  + TCG
  + explicit max or apple-gxf CPU
  + locally supplied authorized VMApple boot material
  + deterministic diagnostics
  + persistent logs
```

The project owner is not required to execute this objective now. Runtime execution remains deferred until the finished integration stage.

## Upstream reference

QEMU documents VMApple as the virtual hardware contract exposed to Apple-Silicon macOS guests by Apple's Virtualization.framework, independently implemented by QEMU.

Current upstream reference:

<https://www.qemu.org/docs/master/system/arm/vmapple.html>

The documented reference command uses:

```text
-M vmapple,uuid=...
-bios AVPBooter.vmapple2.bin
aux image
root disk image
vmapple-virtio-blk-pci
```

The upstream documented path still assumes an Apple-Silicon macOS host and HVF. P1.07 intentionally keeps the guest-side VMApple storage/firmware shape while replacing the accelerator/CPU side with the P1.06 TCG profiles.

## Diagnostic strategy

P1.07 records three evidence streams.

### 1. Launcher log

The harness records safe experiment metadata and combined QEMU stdout/stderr in a unique `.log` file.

It records:

```text
AppleSilicon version
UTC start/end time
host OS
host architecture
QEMU version
selected CPU profile
selected accelerator
SMP count
RAM size
probe duration
input file existence and sizes
hashed UUID identifier
QEMU exit status
whether the harness terminated QEMU at the probe deadline
```

Raw machine UUID values and local proprietary file contents are not written to the launcher log.

### 2. QEMU debug log

QEMU supports `-d` logging categories and `-D` to direct the QEMU log to a file.

P1.07 uses the initial debug set:

```text
guest_errors,unimp,int,cpu_reset
```

`guest_errors` is especially important because QEMU uses that channel to report invalid guest device accesses.

The debug set is intentionally configurable because logging categories can evolve between QEMU revisions.

### 3. Trace events

QEMU's tracing infrastructure supports version-controlled event files and wildcard patterns.

P1.07 begins with:

```text
memory_region_ops_read
memory_region_ops_write
```

These events provide a generic MMIO observation path without modifying every VMApple device implementation just to print register accesses.

The harness first queries `-trace help` and records the available trace points. It only enables configured events that the built QEMU binary actually reports as available.

No Apple boot material is committed to this repository.

```text
APPLESILICON_VMAPPLE_AUX

```

The project repository must never contain:

```text

macOS installers/IPSWs
installed macOS VM disk images
auxiliary VM images
machine secrets
private keys
Apple account credentials
```

## CPU profiles

P1.07 inherits the P1.06 profiles.

### Control

```text
-accel tcg
-cpu max
```

### Apple-oriented experimental

```text
-accel tcg
-cpu apple-gxf
```

`apple-gxf` is an Inferno-provided experimental ARM CPU model. P1.07 does not rename it to M1/M2/M3 or claim that its current register contract matches any physical Apple CPU.

## Launch shape

The generated experiment follows the upstream VMApple storage/firmware layout while making diagnostics explicit:

```text
qemu-system-aarch64
  -no-user-config
  -display none
  -monitor none
  -serial stdio
  -no-reboot
  -m <RAM>
  -smp <CPUS>
  -accel tcg
  -cpu <max|apple-gxf>
  -M vmapple,uuid=<LOCAL_UUID>
  -bios <LOCAL_FIRMWARE>
  -drive file=<LOCAL_AUX>,if=pflash,format=raw
  -drive file=<LOCAL_DISK>,if=pflash,format=raw
  -drive file=<LOCAL_AUX>,if=none,id=aux,format=raw
  -drive file=<LOCAL_DISK>,if=none,id=root,format=raw
  -device vmapple-virtio-blk-pci,variant=aux,drive=aux
  -device vmapple-virtio-blk-pci,variant=root,drive=root
  -d guest_errors,unimp,int,cpu_reset
  -D <QEMU_DEBUG_LOG>
  -trace events=<FILTERED_TRACE_EVENT_FILE>
```

Networking and GUI devices are deliberately omitted from the first divergence probe. They add noise and are not required to identify the earliest CPU/platform incompatibility.

## Finite probe window

A failed firmware or CPU path may spin forever instead of terminating cleanly.

P1.07 therefore includes a configurable finite probe window, defaulting to 30 seconds.

The launcher behavior is:

```text
start QEMU
  ↓
record PID
  ↓
wait for normal QEMU exit OR probe deadline
  ↓
if deadline reached: SIGTERM
  ↓
short grace interval
  ↓
if still alive: SIGKILL
  ↓
record classification and logs
```

A timeout is not classified as success or failure by itself. A spinning CPU may still provide the exact diagnostic evidence needed for the next objective.

## Result classifications

The harness emits a machine-readable classification in the launcher log:

```text
P1_07_PROBE_EXITED
P1_07_PROBE_TIMED_OUT
QEMU_BINARY_MISSING
QEMU_VMAPPLE_MISSING
QEMU_TCG_MISSING
QEMU_CPU_PROFILE_MISSING
INPUT_UUID_MISSING
INPUT_FIRMWARE_MISSING
INPUT_AUX_MISSING
INPUT_DISK_MISSING
TRACE_CAPABILITY_FAILED
LAUNCH_FAILED
```

The exit status is recorded separately from the classification.

## First divergence record

When final integration testing eventually runs this probe, the first meaningful incompatibility is recorded as:

```text
P01-DIVERGENCE-0001

CPU profile:
Stage:
PC, if known:
Instruction/access, if known:
Observed result:
Expected/reference behavior:
Evidence log:
Hypothesis:
Next minimal experiment:
```

Unknown fields remain `unknown`; they must not be guessed.

## Implementation files

P1.07 adds:

```text
.src/.configs/vmapple-preboot.env.example
.src/.configs/p1.07-trace-events
.src/.tools/prepare-p1.07.sh
.src/.tools/run-p1.07-probe.sh
```

`prepare-p1.07.sh` prepares the patched source tree and emits the reproducible probe manifest without launching QEMU.

`run-p1.07-probe.sh` is the runtime launcher reserved for final integration testing. It validates the built QEMU binary and all local inputs before it starts the guest.

## Success condition

P1.07 implementation is complete when:

1. the exact pinned Inferno revision remains fixed,
2. P1.04 and P1.05 are applied in order to disposable source,
3. P1.06 CPU profiles remain explicit,
4. the probe manifest is deterministic,
5. no proprietary input is committed,
6. runtime input validation is fail-closed,
7. every future probe produces persistent launcher and QEMU logs,
8. the probe cannot spin forever without the harness recording a timeout,
9. trace capability discovery occurs before enabling configured trace events,
10. runtime boot success is not falsely claimed before final testing.
