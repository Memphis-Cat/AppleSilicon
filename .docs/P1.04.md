# P1.04 — Decouple VMApple Build From HVF

Project version: **`0.4.0.0.0.0`**

Parent: **Part 01 — VMApple Baseline and Host-Dependency Map**

Status: **Implementation complete — runtime build intentionally deferred**

## Objective

P1.04 removes the compile-time requirement that the VMApple machine can only exist when QEMU is built with Apple's HVF accelerator.

This objective is deliberately narrow.

It does **not** claim that VMApple can boot macOS under TCG or KVM after the patch. It only establishes the prerequisite that a non-HVF AArch64 build can include the VMApple machine model at all.

The project owner is not required to run this objective. Runtime build validation remains deferred under the project-wide final-testing rule.

## Research result

The pinned Inferno revision is:

```text
cc4302a99167abec69b714cfd00c38caece7e7de
```

Its VMApple Kconfig currently contains:

```text
config VMAPPLE
    bool
    depends on ARM
    depends on HVF
    default y if ARM
```

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/vmapple/Kconfig>

The corresponding VMApple Meson file is already keyed only on `CONFIG_VMAPPLE`; it contains no independent HVF condition around `vmapple.c`.

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/vmapple/meson.build>

A source audit of `hw/vmapple/vmapple.c` found only one textual HVF reference:

```c
#include "system/hvf.h"
```

No HVF symbol is otherwise referenced by the VMApple machine implementation at the pinned revision. The include is therefore removed by the P1.04 patch so the machine source no longer advertises a direct HVF source dependency.

## AArch64 scope

P1.04 is not intended to make VMApple a 32-bit ARM machine.

The patch therefore changes the platform gate from:

```text
depends on ARM
depends on HVF
```

to:

```text
depends on ARM
depends on AARCH64
```

This preserves the ARM-family requirement while making the actual 64-bit requirement explicit and removing HVF as a compile-time requirement.

## Important upstream difference

Current upstream QEMU additionally contains:

```text
CONFIG_VMAPPLE=n
```

in the default AArch64 device configuration, because upstream disabled VMApple by default after a macOS 15.4 graphics-related failure.

Our pinned Inferno revision does **not** disable it there; its `CONFIG_VMAPPLE=n` line remains commented.

Therefore P1.04 is intentionally written against the pinned Inferno revision. A future upstream-QEMU rebase will require a separate review of the default device configuration rather than blindly replaying this patch.

Primary upstream references:

<https://github.com/qemu/qemu/blob/master/configs/devices/aarch64-softmmu/default.mak>

<https://github.com/qemu/qemu/commit/49551752e860f5e403cdacac11ee1d218141fd3d>

## Newly exposed boundary: Apple PVG

Removing the HVF Kconfig dependency does not make VMApple host-neutral.

Inferno's build system discovers Apple's `ParavirtualizedGraphics` and Metal frameworks only on Darwin. It sets `CONFIG_MAC_PVG` only when that framework dependency exists for an HVF-capable target. The VMApple machine, meanwhile, selects and realizes an `apple-gfx-mmio` device.

This means a non-Darwin build can move past the VMApple/HVF compile gate and still encounter a later graphics-device boundary.

That is **not** solved in P1.04 because it is a separate hardware-contract problem.

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/meson.build>

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/display/meson.build>

## P1.04 patch

The implementation is stored as:

```text
.src/.patches/0001-vmapple-decouple-build-from-hvf.patch
```

It performs exactly two source-level changes:

```text
1. VMAPPLE depends on AARCH64 instead of HVF.
2. The unused system/hvf.h include is removed from vmapple.c.
```

It deliberately does **not** change:

```text
mc->default_cpu_type = ARM_CPU_TYPE_NAME("host");
```

Changing the CPU contract before VMApple is independently buildable would mix two different objectives.

## Patch preparation harness

P1.04 also introduces:

```text
.src/.tools/prepare-p1.04.sh
```

The harness:

1. verifies the exact pinned Inferno revision,
2. refuses a modified baseline submodule,
3. validates the patch with `git apply --check`,
4. creates a disposable patched source tree under `.build/p1.04/`,
5. applies the patch there rather than modifying the pinned submodule,
6. verifies the HVF Kconfig gate is gone,
7. verifies the AArch64 gate exists,
8. verifies the unused HVF include is gone,
9. verifies the `host` CPU default remains unchanged,
10. writes the entire operation to a unique `.log` file.

The pinned upstream source remains pristine and reproducible.

## P1.04 classifications

The preparation harness records one of the following:

```text
P1_04_PREPARED
SOURCE_UNAVAILABLE
SOURCE_INVALID
SOURCE_REVISION_MISMATCH
SOURCE_DIRTY
PATCH_CHECK_FAILED
PATCH_APPLY_FAILED
POST_PATCH_VALIDATION_FAILED
```

A preparation result is not a runtime VMApple result.

## Success condition

P1.04 implementation is complete when the repository contains a deterministic patch and preparation harness that transform the pinned source so that:

```text
CONFIG_VMAPPLE no longer depends on HVF
CONFIG_VMAPPLE remains ARM/AArch64-only
vmapple.c no longer includes system/hvf.h
VMApple's host CPU default is unchanged
pinned upstream source remains unmodified
all preparation output is logged
```

Actual compilation of the patched tree is intentionally unclaimed until project testing is performed.

## P1.05 boundary

P1.04 exposes the next host dependency before the CPU compatibility work can be meaningful:

```text
P1.05 — Decouple VMApple Machine Realization From Apple PVG
```

The next objective should make the VMApple machine capable of being instantiated without requiring the Darwin-only `apple-gfx-mmio` implementation, while preserving the existing Apple PVG path when it is available.

Only after the machine can be instantiated on a host-neutral path does it make sense to treat the CPU contract as the next first-order runtime blocker.
