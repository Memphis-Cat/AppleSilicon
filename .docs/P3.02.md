# P3.02 — Configuration and Platform Identity Contract

Project version: **`3.1.0.0.0.0`**

Status: **Implementation complete — guest/runtime identity validation intentionally deferred**

## Objective

Define the VMApple configuration-region and platform-identity contract without turning reference defaults into guessed macOS requirements.

P3.02 owns the P3.01 components:

- `configuration_region`
- `platform_identity_values`

It does not own CPU architectural behavior, IRQ/timers, storage, PCIe, AES, or graphics.

## Source result

Pinned Inferno creates `vmapple-cfg` as a 64 KiB RAM-backed SysBus region.

The machine supplies:

- `nr-cpus` from `MachineState.smp.cpus`
- `ecid` from the VMApple machine `uuid` property
- `ram-size` from `MachineState.ram_size`
- `rnd` from `qemu_guest_getrandom_nofail()`

The config device derives:

- `cpu_ids[i] = i` for each configured CPU

The config device also exposes configurable properties for:

- installer flags
- four MAC identities
- serial
- model
- SoC name

Upstream QEMU 11.1.0 source inspected for P3.02 retains the same high-level config behavior, so the contract is not treated as an Inferno-only fork convention.

## Reference defaults are not requirements

Pinned/current VMApple source defaults to:

```text
serial   = "1234"
model    = "VM0001"
soc_name = "Apple M1 (Virtual)"
```

P3.02 records these as `reference_default_only`.

It does **not** claim that macOS requires those strings, nor does it claim that a physical Apple model/serial must be spoofed.

The zero MAC defaults are likewise not promoted to a guest requirement.

## ECID / machine UUID

VMApple exposes a machine property named `uuid` and feeds its 64-bit value directly into the config-region `ecid` field.

P3.02 therefore supports an explicit local `machine_uuid` value for reproducible experiments.

The naming does not prove that this 64-bit value has the semantics or format of a conventional 128-bit UUID, nor does it prove any relationship to physical Apple identifiers beyond the source-backed `uuid -> ecid` wiring.

## Configuration layout discrepancy

P3.02 found an unresolved source-layout discrepancy.

The source declares:

```c
uint32_t cpu_ids[0x80];   /* 0x100 */
uint8_t scratch[0x200];   /* 0x180 */
char serial[32];          /* 0x380 */
```

But `cpu_ids[0x80]` is 128 `uint32_t` elements, or `0x200` bytes.

Starting at `0x100`, that declaration places the following fields at:

```text
cpu_ids  0x100
scratch  0x300
serial   0x500
unk8     0x520
model    0x540
unk9     0x560
unk10    0x580
soc_name 0x584
```

The adjacent comments instead describe:

```text
scratch  0x180
serial   0x380
unk8     0x3a0
model    0x3c0
unk9     0x3e0
unk10    0x400
soc_name 0x404
```

VMApple's machine class caps CPUs at 32, which would require only `0x80` bytes of CPU-ID storage.

That makes the discrepancy important, but it is **not enough evidence to patch the array**. The compiled source may be compatible because later identity fields are unused by the tested guest path, because the intended ABI differs from the comments, or for another reason that must be measured.

P3.02 therefore classifies this as:

```text
unresolved_source_layout_discrepancy
preserve_and_measure_before_any_source_fix
```

No layout patch is added.

## Identity profiles

P3.02 adds a local profile compiler around existing QEMU mechanisms.

QEMU supports global defaults for properties of devices created automatically by a machine. VMApple's config device is such an automatically created device.

A profile can explicitly provide:

```text
machine_uuid
serial
model
soc_name
mac_en0
mac_en1
mac_wifi0
mac_bt0
run_installer1
run_installer2
```

Null identity strings are omitted so upstream defaults remain intact.

The compiler never overrides:

```text
nr-cpus
ram-size
rnd
cpu_ids
```

Those remain machine-derived.

## Privacy rules

Real platform identity material stays local.

Committed examples must be synthetic and synthetic MAC addresses must be unicast, locally administered addresses.

The compiler avoids printing raw identity values in its normal status output. Compiled profile files can contain the local values needed for a later QEMU launch and therefore belong under `.build/`, not in Git.

P3.02 does not require or request:

- Apple ID credentials
- Activation Lock data
- Secure Enclave data
- device certificates
- private keys
- production Apple serial numbers

## Validation

`platform-identity.py` provides:

```text
validate-contract
validate-profile
compile
self-check
```

The self-check rejects, among other things:

- uint64 overflow for the VMApple machine UUID
- oversized fixed-length strings
- option-injection separators in strings
- multicast synthetic MAC addresses
- globally administered synthetic MAC addresses
- invalid installer flags
- an unsupported attempt to mark the layout discrepancy fixed

The logged preparation harness additionally verifies the pinned Inferno source blobs, the config wiring, the layout discrepancy, QEMU's global-property option, and deterministic profile compilation.

## Testing boundary

The Python contract/profile compiler and its synthetic self-check were development-tested while P3.02 was authored.

No macOS guest, HVF VM, TCG VM, real Apple identity, firmware, AUX image, or production machine identifier was used.

Full source-preparation/runtime validation remains deferred under the project testing rule.

## Result

P3.02 establishes a reproducible configuration and identity layer while preserving three unresolved questions for later evidence:

1. which identity fields macOS actually consumes,
2. which values are semantically constrained,
3. whether the CPU-ID array/comment layout discrepancy affects real guest behavior.
