# P3.04 — Boot Backdoor and Storage Contract

Project version: **`3.3.0.0.0.0`**

Status: **Implementation complete — guest/runtime storage validation intentionally deferred**

## Objective

Freeze the VMApple pre-boot backdoor and Apple-specific virtio block contract without inventing storage semantics that are not supported by the pinned source or current upstream QEMU.

P3.04 owns the P3.01 components:

- `bdif_boot_backdoor`
- `vmapple_virtio_block`

It does not own firmware contents, CPU compatibility, configuration identity, interrupt wiring, PCIe host-controller behavior, AES or graphics.

## Result

Pinned Inferno and upstream QEMU 11.1.0 retain the same guest-visible VMApple storage model:

```text
pre-boot environment
        |
        v
BDIF MMIO backdoor
        |
        +--> AUX backend
        +--> root backend

later guest storage
        |
        v
vmapple-virtio-blk-pci
        +--> variant=aux
        +--> variant=root
```

These are two separate access paths over the same reference storage artifacts.

No P3.04 Inferno patch is justified by the available evidence.

## BDIF MMIO contract

VMApple maps the boot backdoor at:

```text
base  0x30000000
size  0x00200000
IRQ   none
```

The device selector is encoded in the upper bits of the MMIO offset:

```text
mask  0xffff0000
root  0x00000000
AUX   0x00010000
USB   0x00100000
```

The source declares the USB selector, but the command handler only services root and AUX.

P3.04 therefore records USB as:

```text
declared_but_not_serviced_by_command_handler
```

and does not infer USB-backed pre-boot storage support.

## BDIF register contract

Pinned Inferno and QEMU expose:

```text
0x000  STATUS       -> 0x1
0x004  CFG          -> 0x2
0x008  UNK1         -> 0x420
0x010  BUSY         -> 0x1
0x400  UNK2         -> 0x1
0x408  CMD          <- guest physical address of VblkReq
0x420  NEXT_DEVICE
0x434  UNK3         -> 0x0
```

For `NEXT_DEVICE`, the current reference values are:

```text
root selector -> 0x08000000
AUX selector  -> 0x00010000
```

P3.04 preserves those values but does **not** assign a speculative semantic name to them. They remain opaque reference values until evidence explains them.

## BDIF request format

The pre-boot request is a DMA-backed structure.

Source geometry:

```text
VblkSector  16 bytes
VblkReqCmd  16 bytes
VblkReq     48 bytes
```

Each `VblkReqCmd` contains:

```text
uint64 address
uint32 length
uint32 flags
```

The request contains commands for:

```text
sector descriptor
data buffer
return value
```

The encoded request fields are converted from little endian before use.

## BDIF sector and size rules

The backing-file offset is:

```text
sector * 512 + static_offset
```

The current VMApple machine passes:

```text
static_offset = 0
```

P3.04 freezes the maximum single BDIF data request at:

```text
128 MiB
```

Requests larger than that are rejected by the current implementation.

## BDIF read/write behavior

The source defines:

```text
READ  flags = 0x00030001
WRITE flags = 0x00010001
```

Read behavior is implemented:

1. DMA-read the request.
2. DMA-read the sector descriptor.
3. Read the requested bytes from the selected block backend.
4. DMA-write them into the guest data buffer.
5. DMA-write one completion byte.

Completion values are:

```text
success = 0
failure = 1
```

The write flag is recognized, but storage writes are not implemented. The source explicitly records the observed pre-boot assumption that iBoot only reads.

The current behavior therefore remains:

```text
read_supported  = true
write_supported = false
```

P3.04 does not implement BDIF writes without evidence that a target guest requires them.

## Storage backend topology

The VMApple machine creates the BDIF device from legacy drive slots.

AUX:

```text
IF_PFLASH unit 0
required
```

Root:

```text
preferred: IF_PFLASH unit 1
fallback:  IF_VIRTIO unit 0
```

The official QEMU VMApple launch topology supplies AUX and root again as ordinary block backends and attaches them to Apple virtio-blk devices:

```text
-drive AUX,if=pflash
-drive DISK,if=pflash

-drive AUX,if=none,id=aux
-drive DISK,if=none,id=root

-device vmapple-virtio-blk-pci,variant=aux,drive=aux
-device vmapple-virtio-blk-pci,variant=root,drive=root
```

This duplication is intentional in the reference launch contract: BDIF uses the pre-boot path while the later guest sees virtio storage.

P3.04 preserves it rather than trying to deduplicate the two attachment paths.

## VMApple virtio-blk identity

The device is:

```text
vmapple-virtio-blk-pci
```

and presents Apple PCI identity:

```text
vendor  0x106b
 device 0x1a00
class   PCI_CLASS_STORAGE_SCSI
```

The virtio PCI machinery may normally choose IDs based on legacy/modern transport, so the VMApple implementation explicitly patches the IDs back to the Apple values after realization.

P3.04 treats those IDs as part of the reference storage contract.

## AUX/root variant contract

QEMU defines the variant enum in this order:

```text
unspecified
root
aux
```

Only `root` and `aux` are valid runtime settings.

An unspecified variant fails device realization.

P3.04 preserves that fail-closed behavior.

## Apple type field

VMApple mostly uses the standard virtio-blk config structure, but stores its AUX/root type identifier in:

```text
virtio_blk_config.max_secure_erase_sectors
```

The implementation writes the `apple_type` variant there with `stl_he_p()`.

To ensure enough config-space storage exists, the device advertises:

```text
VIRTIO_BLK_F_ZONED
```

The implementation does not provide real zoned-block semantics; the source states that the guest is expected to ignore zones.

P3.04 therefore treats this feature as an implementation mechanism for config-space size, not as real zoned-storage support.

## Apple barrier command

VMApple adds:

```text
VIRTIO_BLK_T_APPLE_BARRIER = 0x10000
```

The current implementation:

```text
logs LOG_UNIMP
performs no flush/barrier operation
completes with VIRTIO_BLK_S_OK
```

Pinned Inferno and QEMU 11.1.0 both retain this successful no-op behavior.

P3.04 does not silently turn it into a real flush because that would change guest-visible semantics without evidence.

The contract records:

```text
flush_semantics = unknown_requires_runtime_evidence
```

If a later target macOS version demonstrably depends on ordering or durability guarantees, that becomes an evidence-backed future patch instead of a guess in P3.04.

## AUX image preparation boundary

The official QEMU VMApple documentation prepares the AUX input by skipping one `0x4000`-byte block:

```text
trim block size  0x4000
blocks skipped   1
bytes removed    16384
```

This is an external input-preparation contract, not a reason to commit any Apple-generated AUX image to the repository.

Firmware, AUX and root-disk artifacts remain local external inputs.

## Machine-readable contract

P3.04 adds:

```text
.src/.configs/p3.04-storage-contract.json
```

It records:

- exact Inferno and QEMU source locks;
- BDIF MMIO geometry and selector values;
- source-known BDIF register values;
- DMA request geometry and flags;
- read-only pre-boot behavior;
- backend attachment order/fallback;
- Apple virtio-blk PCI identity;
- AUX/root variant behavior;
- Apple type-field placement;
- no-op barrier semantics;
- external AUX preparation policy.

## Validation tooling

P3.04 adds:

```text
.src/.tools/platform-storage-contract.py
.src/.tools/prepare-p3.04.sh
```

`platform-storage-contract.py` provides:

```text
validate
summary
self-check
verify-source
```

The validator rejects, among other things:

- moving or resizing the BDIF window;
- promoting the declared USB selector to supported storage;
- inventing BDIF write support;
- changing the 512-byte sector contract or 128 MiB request cap;
- changing the pre-boot/runtime backend topology;
- replacing Apple PCI IDs with generic virtio IDs;
- changing AUX/root enum order or permitting `unspecified`;
- moving the Apple type field;
- pretending the zoned feature provides zoned semantics;
- silently changing the Apple barrier into a real flush;
- allowing proprietary storage artifacts into the repository;
- Part 03 scope creep to P3.07.

`prepare-p3.04.sh` performs logged non-guest validation against the exact pinned Inferno source and writes deterministic summaries beneath:

```text
.build/p3.04/
```

Every meaningful preparation run writes:

```text
.logs/AppleSilicon-p3.04-YYYYMMDD-HHMMSS-PID.log
```

It does not open firmware, AUX or root-disk images.

## Source-patch decision

P3.04 adds **no new Inferno patch**.

The current evidence says:

```text
reference semantics exist
        +
pinned Inferno matches them
        +
QEMU 11.1 retains them
        ↓
preserve + validate
```

The two explicitly unresolved semantics are:

```text
BDIF write requirement
Apple barrier flush/ordering requirement
```

Both remain runtime-evidence gated.

## Testing boundary

P3.04's implementation is a development-side static/source contract.

No macOS guest, HVF VM or TCG VM is claimed to have been run for this objective.

No proprietary firmware, AUX image or root disk is required for the contract/self-check layer.

Real guest validation remains reserved for integrated testing.

## Result

P3.04 establishes a deterministic two-phase VMApple boot/storage contract without speculative storage behavior or proprietary inputs.
