# P4.03 — Apple Silicon HVF Reference Capture

Project version: **`4.2.0.0.0.0`**

Status: **Implementation complete — real Apple Silicon/HVF execution deferred**

## Objective

Create the controlled reference-side runtime capture that corresponds to the P4.02 TCG probe while preserving Part 01 as the evidence authority.

The reference role is fixed to:

```text
machine      vmapple
accelerator  hvf
cpu          host
host OS      Darwin
host arch    arm64
RAM          4G / 4096 MiB
vCPUs        4
capture      30 seconds
grace        3 seconds
```

P4.03 must fail closed when the required Apple Silicon reference host is unavailable.

## Why the reference must be real Apple Silicon

The reference is intended to keep the VMApple device model and guest inputs constant while replacing the experimental TCG/`apple-gxf` CPU path with QEMU's HVF/`host` path on Apple Silicon.

An Intel macOS host cannot satisfy that contract. P4.03 therefore does not permit a substitute reference classification.

## Current QEMU contract

Current QEMU VMApple documentation still describes the VMApple machine as an Apple-Silicon/macOS-hosted machine and demonstrates the HVF launch path with the same VMApple firmware/AUX/root topology used by this project.

The QEMU command-line interface also exposes `-machine help`, `-accel help`, `-cpu help`, and `-version`; P4.01/P4.03 use those interfaces to verify the selected reference binary before execution.

## Reused Part 01 runtime path

P4.03 does not implement a second HVF launcher.

It reuses:

```text
.src/.tools/run-p1.09-reference.sh
```

That runner already enforces Darwin/arm64, selects:

```text
-accel hvf
-cpu host
-M vmapple,uuid=<redacted>
```

captures the Part 01 MMIO trace/debug contract and emits a sanitized P1.09 reference manifest.

## Runtime parameter equality with P4.02

P4.03 locks the same comparison-sensitive parameters as P4.02:

```text
RAM      4G / 4096 MiB
SMP      4
window   30 seconds
grace    3 seconds
```

RAM and SMP are subsequently recorded by the P1.09 manifest and become part of P4.04 comparability.

## Preflight

Before execution, `reference-capture.py preflight` requires:

1. a valid P4.01 `reference` session plan;
2. host `Darwin/arm64`;
3. the exact P3.06 integration manifest bound by that plan;
4. the exact planned QEMU SHA-256, size and version;
5. `vmapple`, `hvf`, and `host` capabilities;
6. exact firmware/AUX/root/machine-identity digests;
7. optional hardware-model digest equality;
8. canonical machine-UUID digest equality;
9. the Part 01 trace/debug contract.

No raw UUID or guest-input path is written into the preflight result.

## Reference execution

`run-p4.03-reference.sh` forces the P4.03 runtime contract and delegates to `run-p1.09-reference.sh`.

The wrapper requires the resulting launcher to report:

```text
Host OS: Darwin
Host architecture: arm64
Accelerator: hvf
CPU profile: host
SMP: 4
RAM: 4G
Reference seconds: 30
Classification: P1_09_REFERENCE_*
```

The resulting reference manifest is revalidated using the existing P1.09 validator.

## Launcher-log asymmetry

The existing P1.09 reference manifest records:

```text
serial_log
qemu_debug_log
trace_capability_log
```

but does not record its launcher log as a manifest artifact.

P4.03 intentionally does **not** alter the closed P1.09 format. Instead, the P4.03 capture descriptor hashes the launcher log separately while preserving the original P1.09 reference manifest byte-for-byte.

## Postflight

After the reference run, P4.03 repeats the full preflight and requires the pre-run and post-run canonical files to be byte-identical.

Any QEMU, UUID, platform-manifest or guest-input change during execution invalidates the capture.

## Outputs

A real future reference run produces local artifacts under:

```text
.build/p4.03/<run>/preflight-before.json
.build/p4.03/<run>/preflight-after.json
.build/p4.03/<run>/reference-manifest.json
.build/p4.03/<run>/reference-capture.json
```

The final capture classification is:

```text
P4_03_REFERENCE_CAPTURE_READY
```

It binds the reference session fingerprint, platform fingerprint, P1.09 reference manifest, runtime artifacts and launcher-log digest.

## Evidence boundary

`P4_03_REFERENCE_CAPTURE_READY` means only that the reference observation has valid provenance.

It does **not** mean:

- macOS successfully booted;
- TCG diverged from HVF;
- a CPU/system-register requirement was identified;
- a divergence was promoted.

P1.10 remains the only divergence-promotion authority.
