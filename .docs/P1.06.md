# P1.06 — Explicit Non-Host VMApple CPU Selection

Project version: **`0.6.0.0.0.0`**

Parent: **Part 01 — VMApple Baseline and Host-Dependency Map**

Status: **Implementation complete — runtime CPU probe intentionally deferred**

## Objective

P1.06 establishes a deterministic way to select a non-`host` ARM64 CPU for VMApple without replacing QEMU's existing CPU-selection architecture and without changing the known-good Apple/HVF reference default.

The objective is deliberately about **selection**, not Apple CPU compatibility.

After P1.06 the project can describe an experiment as:

```text
VMApple
  + TCG
  + explicit CPU model
```

rather than relying on VMApple's default:

```text
VMApple
  + host CPU
```

No claim is made that `max`, `apple-gxf`, or any other current QEMU CPU model is sufficient to boot modern macOS.

The project owner is not required to run this objective. Runtime CPU probing remains deferred under the project-wide final-testing rule.

## Research result — VMApple already accepts an explicit CPU

The pinned Inferno revision remains:

```text
ChefKissInc/Inferno
cc4302a99167abec69b714cfd00c38caece7e7de
```

VMApple defines its reference default as:

```c
mc->default_cpu_type = ARM_CPU_TYPE_NAME("host");
```

However, the VMApple CPU list is not hard-coded to `host`. The machine fills every possible CPU entry from:

```c
ms->possible_cpus->cpus[n].type = ms->cpu_type;
```

and later constructs CPUs from those entries.

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/hw/vmapple/vmapple.c>

QEMU's startup path first assigns the machine default and then replaces it when the user supplied `-cpu`:

```c
current_machine->cpu_type = machine_class_default_cpu_type(machine_class);
if (cpu_option) {
    current_machine->cpu_type = parse_cpu_option(cpu_option);
}
```

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/system/vl.c>

`parse_cpu_option()` resolves a named CPU model to the concrete QOM CPU type and applies any requested CPU feature properties before the machine creates CPUs.

Current upstream reference:

<https://github.com/qemu/qemu/blob/master/hw/core/cpu-common.c>

Therefore a third VMApple source patch is **not required merely to select a non-host CPU**.

Adding a new VMApple-specific CPU-selection system would duplicate an existing QEMU mechanism and create unnecessary maintenance work.

## P1.06 CPU profiles

P1.06 defines two non-host TCG profiles.

### Profile A — `max`

```text
accelerator = tcg
cpu         = max
machine     = vmapple
```

`max` is the neutral control profile.

At the pinned Inferno revision, `-cpu max` under TCG begins from its Cortex-A57 model and then enables the additional features implemented by Inferno/QEMU's maximum TCG CPU path.

This profile gives us the broadest generic QEMU ARM64 baseline without deliberately enabling Inferno's Apple GXF feature.

### Profile B — `apple-gxf`

```text
accelerator = tcg
cpu         = apple-gxf
machine     = vmapple
```

The pinned Inferno tree already contains an `apple-gxf` CPU model.

Its initialization path:

1. begins from Inferno's `max` CPU model,
2. changes the exposed pointer-authentication feature field,
3. enables `pauth-noop` while using TCG,
4. enables Inferno's `ARM_FEATURE_GXF` Apple-oriented feature path.

Primary source:

<https://github.com/ChefKissInc/Inferno/blob/cc4302a99167abec69b714cfd00c38caece7e7de/target/arm/cpu64.c>

This makes `apple-gxf` a valuable experimental comparison profile, but it must **not** be described as a complete Apple Silicon CPU.

It comes from Inferno's broader Apple ARM emulation work and does not by itself provide every CPU-visible behavior required by modern macOS.

## Reference profile — `host`

`host` remains the reference VMApple default.

P1.06 does not remove or replace it.

```text
Apple Silicon host
    + HVF
    + -cpu host/default
```

remains useful later for differential tracing against:

```text
TCG + -cpu max
TCG + -cpu apple-gxf
```

The P1.06 non-host profile generator rejects `host` deliberately so an experiment intended to be generic cannot silently fall back to the real host CPU.

## Why P1.06 does not patch the default to `max`

Changing:

```c
mc->default_cpu_type = ARM_CPU_TYPE_NAME("host");
```

to:

```c
mc->default_cpu_type = ARM_CPU_TYPE_NAME("max");
```

would make the source look more generic but would damage the reference path and hide whether an experiment actually selected its CPU deliberately.

The stronger contract is:

```text
no -cpu supplied
    -> keep upstream/reference host behavior

non-host experiment
    -> require explicit -cpu max or -cpu apple-gxf
```

That keeps reference and experimental paths separate.

## P1.06 implementation files

P1.06 introduces:

```text
.src/.configs/vmapple-cpu.env.example
.src/.tools/prepare-p1.06.sh
```

No `0003` VMApple source patch is created in this objective because the existing QEMU CPU option already supplies the required mechanism.

## Configuration contract

The example configuration defines:

```text
APPLESILICON_VMAPPLE_ACCEL=tcg
APPLESILICON_VMAPPLE_CPU_PROFILE=max
APPLESILICON_VMAPPLE_SMP=4
```

Accepted non-host CPU profiles are:

```text
max
apple-gxf
```

`host` is intentionally rejected by the P1.06 non-host preparation path.

## Preparation harness

`.src/.tools/prepare-p1.06.sh` performs source-level preparation only.

It:

1. validates the exact pinned Inferno revision,
2. refuses a dirty tracked upstream baseline,
3. verifies P1.04 and P1.05 patches apply,
4. creates a disposable source tree under `.build/p1.06/`,
5. applies P1.04 and P1.05 in order,
6. verifies VMApple still has the `host` reference default,
7. verifies VMApple sources possible CPUs from `ms->cpu_type`,
8. verifies Inferno's startup path replaces the default when `-cpu` is supplied,
9. verifies both `max` and `apple-gxf` CPU definitions exist in the pinned tree,
10. verifies P1.04's non-HVF build change remains present,
11. verifies P1.05's optional-PVG construction remains present,
12. rejects a non-TCG accelerator for this objective,
13. rejects the `host` CPU profile,
14. emits deterministic selected-profile metadata under `.build/p1.06/`,
15. writes the complete operation to a unique `.log` file.

It does **not** boot firmware or macOS.

## Emitted profile

A successful preparation emits:

```text
.build/p1.06/vmapple-cpu-profile.env
```

with the exact experiment identity, for example:

```text
APPLESILICON_VMAPPLE_ACCEL=tcg
APPLESILICON_VMAPPLE_CPU_PROFILE=max
APPLESILICON_VMAPPLE_MACHINE=vmapple
APPLESILICON_VMAPPLE_SMP=4
APPLESILICON_VMAPPLE_QEMU_ARGS=-accel tcg -cpu max -M vmapple -smp 4
```

This is metadata for a later launcher, not a complete macOS boot command. Firmware, AUX storage, root storage, UUID, and other guest inputs remain separate later-stage configuration.

## Success condition

P1.06 is implementation-complete when the project has a reproducible and logged way to state:

```text
reference:
    VMApple -> host

control:
    VMApple -> TCG -> max

experimental:
    VMApple -> TCG -> apple-gxf
```

while preserving:

```text
VMApple's upstream host default
P1.04 non-HVF build path
P1.05 optional Apple PVG path
pinned Inferno revision
no proprietary Apple material
persistent logs
```

Runtime CPU compatibility remains intentionally unclaimed until final project testing.

## P1.07 boundary

P1.06 gives us an explicit generic CPU path. The next objective can finally construct the **first controlled TCG VMApple launch specification** around it.

The expected next objective is:

```text
P1.07 — TCG VMApple Pre-Boot Probe Harness
```

P1.07 should assemble the patched VMApple build, explicit CPU profile, deterministic QEMU diagnostics, and non-secret local guest-path placeholders into one logged probe launcher.

Its purpose will be to preserve the earliest real failure when VMApple is finally driven toward TCG rather than continuing to remove prerequisites blindly.
