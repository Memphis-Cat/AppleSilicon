# P2.04 — CPU Feature and ID-Register Compatibility

Project version: **`2.3.0.0.0.0`**

Status: **Implementation complete — architectural feature profile only**

## Objective

P2.04 defines the architectural CPU-visible minimum that the TCG `apple-gxf` VMApple path must expose through standard AArch64 feature/ID registers.

This objective is separate from P2.03:

```text
P2.03 = Apple implementation-defined system-register semantics
P2.04 = architectural ARM feature and ID-register exposure
```

P2.04 does not emulate an M-series microarchitecture and does not assign HID/GXF/SPRR/AMX register semantics.

## Primary guest-side contract

The source lock is Apple XNU:

```text
repository: apple-oss-distributions/xnu
revision: f6217f891ac0bb64f3d375211650a4c1ff8ca1ea
path: pexpert/pexpert/arm64/VMAPPLE.h
blob: 08b35780a1dcf187af2ced7839d7045afb433de7
```

That VMApple configuration explicitly declares:

```text
CPU_HAS_APPLE_PAC
HAS_PARAVIRTUALIZED_PAC
HAS_ARM_FEAT_SSBS2
HAS_ARM_FEAT_SME
HAS_ARM_FEAT_SME2
HAS_ARM_FEAT_PAN3
__ARM_16K_PG__
__ARM_RANGE_TLBI__
__ARM_MIXED_PAGE_SIZE__
```

It also declares platform contracts such as GICv3 and paravirtualized CTRR. Those are not CPU ID-register fields and are deferred to their owning platform/device work.

## Pinned Inferno capability baseline

Pinned Inferno remains:

```text
cc4302a99167abec69b714cfd00c38caece7e7de
```

Its TCG `max` CPU already exposes the architectural capabilities required by the VMApple XNU configuration, including:

```text
ID_AA64ISAR0_EL1.TLB     = 2   -> FEAT_TLBIRANGE
ID_AA64PFR1_EL1.SSBS     = 2   -> FEAT_SSBS2
ID_AA64PFR1_EL1.SME      = 2   -> SME2-capable profile
ID_AA64MMFR0_EL1.TGRAN16 = 1   -> 16 KiB stage-1 granule
ID_AA64MMFR1_EL1.PAN      = 3   -> FEAT_PAN3
ID_AA64SMFR0_EL1.SMEVER   = 2   -> SME2.1 in the current max model
```

`max` also provides 4 KiB stage-1 translation support and PAuth infrastructure.

Therefore P2.04 does not replace the full `max` feature set. It establishes a project-owned minimum on top of it.

## Implemented patch

P2.04 adds:


The patch creates:

```text
target/arm/apple-cpu-features.h
target/arm/apple-cpu-features.c
```

and wires the profile only into the existing TCG `apple-gxf` initializer.

Resulting structure:

```text
aarch64_apple_gxf_initfn
    |
    +-- aarch64_max_initfn
    +-- existing Apple-oriented PAuth setup
    |
    +-- if TCG
           |
           +-- pauth-noop property
           +-- apple_cpu_feature_profile_init()
           +-- apple_sysreg_framework_init()
```

The ordinary `max` CPU remains untouched.

The host/HVF and KVM CPU paths remain untouched.

## Minimum architectural profile

### Pointer authentication

XNU declares:

```text
CPU_HAS_APPLE_PAC
```

P2.04 requires PAuth to remain present on `apple-gxf`.

It deliberately does **not** select a new PAuth algorithm. Inferno's existing `apple-gxf`/TCG PAuth setup remains responsible for that mechanism.

`HAS_PARAVIRTUALIZED_PAC` is recorded separately because paravirtualized PAC behavior is not described solely by architectural ID-register fields.

### SSBS2

Minimum:

```text
ID_AA64PFR1_EL1.SSBS >= 2
```

### SME and SME2

Minimum:

```text
ID_AA64PFR1_EL1.SME >= 2
ID_AA64SMFR0_EL1.SMEVER >= 1
```

A stronger value already provided by QEMU is preserved.

### PAN3

Minimum:

```text
ID_AA64MMFR1_EL1.PAN >= 3
```

This is only ID-register exposure.

XNU's `APPLEVIRTUALPLATFORM` path separately documents that `SCTLR_EL1.EPAN` may behave as read-as-zero/write-ignored on some hosts. P2.04 therefore does not invent SCTLR semantics.

### Translation granules

VMApple XNU declares both:

```text
__ARM_16K_PG__
__ARM_MIXED_PAGE_SIZE__
```

P2.04 therefore requires stage-1 support for both:

```text
4 KiB
16 KiB
```

It does not force stage-2 granule behavior because stage-2 belongs to the hypervisor/accelerator side rather than the guest's stage-1 pmap contract.

### Range TLBI

XNU declares:

```text
__ARM_RANGE_TLBI__
```

P2.04 requires:

```text
ID_AA64ISAR0_EL1.TLB = 2
```

which is the feature level used by QEMU for FEAT_TLBIRANGE.

## Preserve-stronger rule

The profile is a minimum contract.

For ordered feature fields:

```text
current stronger value -> preserved
current weaker value   -> raised to minimum
```

For support encodings such as 4 KiB translation granules, an already supported encoding is preserved.

This avoids downgrading QEMU's `max` CPU merely to imitate a guessed physical Apple CPU.

## Development-side validation

P2.04 adds:

```text
.src/.tools/prepare-p2.04.sh
```

The logged harness:

1. validates the P2.01 inventory;
2. validates the P2.04 machine-readable contract;
3. checks the exact Inferno source revision;
4. verifies pinned Inferno actually implements the required architectural features;
5. verifies the current TCG `max` baseline exposes the expected feature encodings;
6. applies patches `0001` through `0005` to a disposable source tree;
7. verifies the new feature source is compiled for AArch64;
8. verifies the profile is attached only to TCG `apple-gxf`;
9. verifies the ordinary `max` path is not contaminated;
10. verifies the feature minimums and postconditions;
11. verifies P2.03 still has zero live implementation-defined sysreg policies;
12. runs `git diff --check`.

Each run writes:

```text
.logs/AppleSilicon-p2.04-YYYYMMDD-HHMMSS-PID.log
```

No macOS guest is launched.

## What P2.04 proves

P2.04 proves that the project no longer relies on an undocumented assumption that whatever QEMU `max` happens to expose is automatically the VMApple CPU contract.

The project now owns a source-backed minimum architectural profile:

```text
XNU VMAPPLE declarations
        |
        v
P2.04 feature contract
        |
        v
apple-gxf TCG ID registers
```

It does not prove that these features alone are sufficient to boot macOS.

## Exit criteria

P2.04 is implementation-complete when the XNU VMApple feature source is locked, the architectural requirements are machine-readable, the TCG `apple-gxf` profile enforces those minimums without altering `max`/HVF/KVM, non-ID platform contracts remain deferred, P2.03 sysreg semantics remain unchanged, and the logged preparation path validates the complete patch series.
