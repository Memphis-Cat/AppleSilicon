# P2.01 — Apple CPU System Register and Feature Inventory

Project version: **`2.0.0.0.0.0`**

Parent: **Part 02 — Apple CPU Compatibility Contract**

Status: **Implementation complete — static inventory only**

## Objective

P2.01 creates the first machine-readable CPU contract for AppleSilicon.

Part 01 intentionally deferred the real HVF-versus-TCG macOS experiment. That means there is no legitimate runtime result telling us which Apple CPU behavior fails first.

P2.01 therefore does not guess the first blocker.

Instead it answers a narrower question:

> What Apple implementation-defined AArch64 register space and guest-visible architectural behavior do our primary sources prove exists, and what can we safely prepare for emulation without yet claiming macOS requires it?

## Primary-source basis

P2.01 locks exact source artifacts.

### Apple XNU

```text
repository: apple-oss-distributions/xnu
revision:   f6217f891ac0bb64f3d375211650a4c1ff8ca1ea
path:       osfmk/arm64/proc_reg.h
blob:       2b6d7231cb1db4ee4f1a26e4775b5284de332acf
```

XNU provides the public guest-side evidence for ARM64 register/feature policy.

Important observations include:

- a dedicated `VMAPPLE` cache-configuration branch;
- `APPLEVIRTUALPLATFORM` behavior;
- an explicitly optional `SCTLR_EL1.EPAN` behavior on the virtual platform;
- conditional Apple pointer-authentication policy;
- 4 KiB/16 KiB translation-granule definitions and mixed-page-size support paths.

These are guest-visible requirements/tolerances, but P2.01 does not turn every XNU compile-time feature into a VMApple requirement.

### QEMU

```text
repository: qemu/qemu
revision:   3e3ccab106f879b1512f8e0d51a827dd4de30e22
path:       target/arm/cpregs.h
blob:       391c0e322b7097ccf05b9fc2edc04b0e5cc821e7
```

QEMU already represents AArch64 system registers using the same fundamental encoding fields needed by the Apple register inventory:

```text
op0
op1
CRn
CRm
op2
```

`ARMCPRegInfo` also supplies the future implementation hooks for access rights, reads, writes, resets and special behavior.

P2.01 uses that as the intended future integration surface. It does not patch QEMU yet.

### Asahi m1n1

```text
repository: AsahiLinux/m1n1
revision:   06a4601a351ebfd1abb6abba9a44c34e40d94776
path:       src/cpu_regs.h
blob:       f40cc8a9e507418e204522be121ac262b314ca41
```

m1n1 provides an open source encoding reference for a large Apple implementation-defined system-register space.

P2.01 imports an initial CPU-focused subset including:

```text
HID / EHID
Apple timer aliases/control
AMX control registers
GXF / SPRR
Apple pointer-authentication control registers
selected hypervisor/control registers
```

Large PMU/UPM, error-status and energy-accounting families are acknowledged but left outside the initial boot-oriented contract until evidence makes them relevant.

### Inferno

```text
repository: ChefKissInc/Inferno
revision:   cc4302a99167abec69b714cfd00c38caece7e7de
```

Inferno remains the pinned VMApple/TCG implementation base inherited from Part 01.

P2.01 does not modify the pinned submodule.

## Machine-readable contract

P2.01 adds:

```text
.src/.configs/p2.01-cpu-contract.json
```

Every register entry stores:

```text
name
architectural_name
encoding
class
group
source_evidence
xnu_relevance
observed_access
runtime_priority
implementation_state
notes
```

An example:

```json
{
  "name": "HID0",
  "architectural_name": "S3_0_C15_C0_0",
  "encoding": {
    "op0": 3,
    "op1": 0,
    "crn": 15,
    "crm": 0,
    "op2": 0
  },
  "class": "apple_implementation_defined",
  "group": "hid_ehid",
  "xnu_relevance": "unknown",
  "observed_access": [],
  "runtime_priority": "unknown",
  "implementation_state": "inventory_only"
}
```

The empty `observed_access` value is deliberate.

The fact that m1n1 knows a register encoding does not prove that our target macOS/VMApple path reads or writes it.

## No guessed semantics

P2.01 records **encodings**, not fake implementations.

It does not assign:

- reset values,
- read values,
- writable masks,
- trap behavior,
- side effects,
- per-core versus shared storage,
- migration behavior,

unless a primary source establishes them and a later objective deliberately adopts them.

Every imported register starts as:

```text
runtime_priority = unknown
implementation_state = inventory_only
```

This prevents a long list of physical-Mac registers from turning into hundreds of invented emulator behaviors.

## Why the VMApple distinction matters

Public XNU explicitly contains virtual-platform behavior.

One particularly useful example is `SCTLR_EL1.EPAN`: on `APPLEVIRTUALPLATFORM`, XNU treats that bit as optional because it may behave as read-as-zero/write-ignored on some hosts.

That is exactly the type of compatibility tolerance we want to identify.

It demonstrates why the project cannot assume:

```text
physical Apple implementation
=
VMApple contract
```

## P2.01 tool

P2.01 adds:

```text
.src/.tools/cpu-contract.py
```

Commands:

```text
validate
summary
lookup
self-check
```

### validate

The validator checks:

- schema/version/objective identity;
- exact required source identities;
- unique register names;
- unique AArch64 encoding tuples;
- valid `op0/op1/CRn/CRm/op2` ranges;
- canonical `Sx_x_Cx_Cx_x` name consistency;
- allowed class/group/access states;
- evidence references resolve to known sources;
- P2.01 runtime priority remains `unknown`;
- P2.01 implementation state remains `inventory_only`;
- feature entries remain inventory-only;
- next objective is exactly P2.02.

### summary

Produces counts by register group and feature class without changing the contract.

### lookup

Displays the exact machine-readable record for one named register.

### self-check

Uses in-memory mutations to ensure the validator rejects:

- duplicate names;
- duplicate encodings;
- out-of-range encoding fields;
- fabricated runtime priority;
- premature implementation state;
- broken architectural names;
- unknown evidence sources.

No emulator or guest is launched.

## Development-side preparation

P2.01 adds:

```text
.src/.tools/prepare-p2.01.sh
```

The script:

1. creates a persistent P2.01 `.log`;
2. checks JSON syntax;
3. compiles the Python source in memory without creating `__pycache__`;
4. runs contract validation;
5. runs the deterministic self-check;
6. prints the contract summary;
7. verifies representative HID0 and GXF register lookups;
8. records the final status.

It does not run:

```text
QEMU
macOS
HVF
TCG guest execution
m1n1
```

## Imported register groups

The initial contract contains these groups:

```text
hid_ehid
timer
amx
gxf_sprr
pauth_control
control_hypervisor
```

This is intentionally a CPU bring-up inventory, not a complete dump of every Apple PMU/debug/error/energy register known to m1n1.

The following families are explicitly tracked as deferred:

```text
apple_pmu_upm
apple_error_status
apple_energy_accumulators
```

They can be promoted into the active contract only when a later objective has a reason.

## Acceptance conditions

P2.01 is implementation-complete when:

1. Part 02 has a fixed objective list;
2. exact primary-source identities are recorded;
3. Apple register encodings are machine-readable;
4. register names and encoding tuples are unique;
5. physical-Apple evidence is not mislabeled as VMApple necessity;
6. XNU virtual-platform behavior is represented separately from physical Apple implementation-defined registers;
7. no register reset/read/write semantics are invented;
8. a deterministic validator/self-check exists;
9. the preparation path writes a `.log`;
10. no maintainer guest test is required.

## What P2.01 does not prove

P2.01 does **not** prove:

- macOS reads HID0 under VMApple;
- GXF or SPRR is required by VMApple;
- AMX is required for boot;
- any imported register needs nonzero state;
- any register should read as zero;
- any write should be ignored;
- an M1/M2/M3/M4/M5 CPU has been emulated;
- the TCG guest boots.

Those statements require later implementation evidence or real runtime evidence.
