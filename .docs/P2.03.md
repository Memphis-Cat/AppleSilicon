# P2.03 — Register Read/Write/Reset Policy Model

Project version: **`2.2.0.0.0.0`**

Status: **Implementation complete — policy engine only**

## Objective

P2.03 turns the P2.02 Apple system-register framework into an explicit, data-driven policy engine.

The objective is:

> Make read, write, reset and access behavior independently reviewable, require evidence/scope metadata before behavior can be attached, and preserve undefined behavior when semantics are still unknown.

P2.03 does not claim that any P2.01 Apple implementation-defined register is required by VMApple.

The live policy table remains empty because the source-locked P2.01 inventory has not yet promoted any register from `inventory_only` to an evidence-backed runtime behavior.


## Policy dimensions

The policy object separates four concerns.

### Read policy

```text
undefined
stored
zero
constant
callback
```

### Write policy

```text
undefined
store
ignore
callback
```

### Reset policy

```text
none
value
callback
```

### Access policy

```text
allow
undefined
trap_el1
trap_el2
trap_el3
callback
```

This separation prevents a convenient combined mode such as “read zero / ignore writes” from being silently assigned when only one half of the behavior is known.

## Evidence and scope

Every semantic `AppleSysRegPolicy` must provide non-empty:

```text
evidence
scope
```

The registration path asserts both before building an `ARMCPRegInfo`.

`evidence` records why the behavior is justified.

`scope` records where the behavior is intended to apply, for example a specific virtual-platform path, CPU generation, authorized trace result, or public XNU-observed contract.

P2.03 does not treat the existence of an m1n1 register encoding as evidence for a VMApple semantic policy.

## QEMU policy mapping

P2.03 uses QEMU/Inferno's existing cpreg mechanisms.

The policy compiler maps behavior to:

```text
undefined access       -> CP_ACCESS_UNDEFINED
read as zero          -> arm_cp_read_zero
write ignored         -> arm_cp_write_ignore
constant read         -> ARM_CP_CONST
stored state          -> ARMCPRegInfo.fieldoffset
reset value           -> ARMCPRegInfo.resetvalue
no reset with state   -> arm_cp_reset_ignore
EL1/EL2/EL3 trap      -> CP_ACCESS_TRAP_EL1/EL2/EL3
policy metadata       -> define_one_arm_cp_reg_with_opaque
```

Callback policies use QEMU's existing `CPReadFn`, `CPWriteFn`, `CPResetFn` and `CPAccessFn` hooks.

## Stored-state rule

P2.03 does not allocate fabricated per-CPU fields for unknown Apple registers.

A stored policy must explicitly provide a valid existing `CPUARMState` field offset.

This has two consequences:

1. a future objective cannot accidentally create generic anonymous state merely because a register needs to stop trapping;
2. adding state becomes a reviewable implementation change tied to a concrete evidence-promoted register.

If state exists, reset behavior must also be explicit.

`reset = none` maps to `arm_cp_reset_ignore`.

`reset = value` maps to `ARMCPRegInfo.resetvalue`.

`reset = callback` requires a reset callback.

## Constant policy rule

`read = constant` is only legal with:

```text
write = ignore
reset = none
has_field = false
```

This maps cleanly to QEMU's `ARM_CP_CONST` behavior rather than creating an unnecessary backing field.

The constant value itself must still be evidence-backed.

## Callback rule

A callback pointer is required only when its corresponding policy kind is `callback`.

A dormant callback is rejected when the declared policy is not callback-driven.

## Unknown behavior remains fail-closed

P2.03 keeps the P2.02 explicit undefined helper.

Inside the semantic policy path, an undefined read or write is checked before the general access policy.

Therefore unknown reads cannot silently become zero reads, and unknown writes cannot silently become write-ignore or storage.

## Duplicate encoding guard

Before a policy table is installed, P2.03 compares every encoding pair.

Two policies may not claim the same `op0/op1/CRn/CRm/op2` tuple.

Every run writes:

```text

```

## What P2.03 proves

P2.03 proves that AppleSilicon can represent a register contract as:

```text
encoding
+ read policy
+ write policy
+ reset policy
+ access policy
+ evidence
+ scope
```

and translate it into QEMU's native `ARMCPRegInfo` machinery.

It does not prove any specific Apple implementation-defined register semantics.

## Guest status

No guest execution is claimed for P2.03.

## Exit criteria

P2.03 is implementation-complete when the four policy dimensions are explicit, policies require evidence/scope, unknown reads/writes remain undefined, stored/reset behavior is explicit, supported policies map to QEMU native cpreg mechanisms, duplicate encodings are rejected, the live policy table remains empty until evidence promotes a register, and the logged patch-series validator passes.
