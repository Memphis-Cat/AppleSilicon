# P4.02 — Integrated TCG Probe Capture

Project version: **`4.1.0.0.0.0`**

Status: **Implementation complete — real TCG probe execution intentionally deferred**

## Objective

Turn the P4.01 probe session provenance lock into one controlled TCG runtime capture while preserving the existing authoritative runtime chain:

```text
P4.01 probe session plan
        ↓
P4.02 preflight
        ↓
P3.06 platform runtime wrapper
        ↓
P2.06 CPU runtime wrapper
        ↓
P1.07 authoritative TCG probe
        ↓
P1.10 probe collector
        ↓
P1.09 validated probe manifest
        ↓
P4.02 postflight + capture manifest
```

P4.02 does not introduce another QEMU command builder.

## Fixed runtime contract

P4.02 fixes the probe execution to:

```text
machine          vmapple
accelerator      tcg
CPU              apple-gxf
RAM              4G / 4096 MiB
SMP              4
capture window   30 seconds
grace window     3 seconds
```

The RAM/SMP lock closes a provenance gap left intentionally outside the P4.01 session plan. P1.09 already records RAM and SMP and requires them to match between reference and probe; P4.02 therefore freezes them before the first real probe is admitted.

## Trace contract

The capture continues to use the Part 01 trace contract:

```text
memory_region_ops_read
memory_region_ops_write
```

and QEMU debug categories:

```text
guest_errors
unimp
int
cpu_reset
```

Current QEMU tracing documentation confirms that an events file can enable trace events from process start and that the default log backend writes trace events to stderr when no explicit trace backend was configured.

Primary source:

- https://www.qemu.org/docs/master/devel/tracing.html

## Preflight and postflight

Before the guest is allowed to run, `probe-capture.py preflight` verifies that the local state still matches the P4.01 session plan:

- P3.06 integration-manifest digest and platform fingerprint;
- QEMU executable SHA-256 and byte size;
- QEMU first version line;
- `vmapple`, `tcg`, and `apple-gxf` capabilities;
- firmware digest and byte size;
- AUX digest and byte size;
- root-disk digest and byte size;
- machine-identity digest and byte size;
- optional hardware-model digest and byte size;
- canonical machine-UUID digest;
- trace/debug contract.

The same preflight is repeated after the runtime completes. The two canonical JSON results must be byte-identical.

Therefore changing QEMU or any guest input while the guest is executing invalidates the capture.

## Runtime delegation

`run-p4.02-probe.sh` does not execute QEMU directly.

It delegates to `run-p3.06-probe.sh`, which delegates to P2.06 and finally the single P1.07 QEMU launcher.

This preserves one authoritative observational launch implementation.

## Runtime result

A completed P1.07 result may be either:

```text
P1_07_PROBE_EXITED
P1_07_PROBE_TIMED_OUT
```

A timeout is still an observation. It is not automatically a failure or a divergence.

Launch/configuration/capability failures prevent P4.02 capture finalization.

## P1.09 probe manifest

After a completed P1.07 observation, P4.02 invokes the existing `collect-p1.10-probe.sh` collector.

That collector creates a P1.09-compatible sanitized manifest containing:

- runtime start/end/result;
- host metadata;
- TCG / `apple-gxf` machine contract;
- 4096 MiB RAM and 4 vCPUs;
- trace/debug contract;
- guest-input SHA-256 digests and sizes;
- launcher-log digest;
- serial-log digest;
- QEMU-debug-log digest;
- trace-capability-log digest.

The generated manifest must pass `reference-manifest.py validate` before P4.02 continues.

## Capture manifest

P4.02 then emits a local sanitized capture descriptor:

```text
.build/p4.02/<run>/probe-capture.json
```

It binds:

- P4.01 session fingerprint;
- P3.06 platform-integration fingerprint;
- P4.02 preflight fingerprint;
- P1.09 probe-manifest digest;
- P1.07 run ID/result/timestamps;
- guest-input digests;
- trace contract;
- runtime artifact digests.

No local paths, raw UUID, firmware contents, disk contents, or machine-identity contents are stored in the capture manifest.

## Promotion boundary

P4.02 does **not** compare reference/probe traces and does **not** promote a divergence.

The authoritative promotion path remains P1.10.

A P4.02 capture therefore says only:

> This TCG observation was produced from the exact locked probe provenance and has a valid P1.09 runtime manifest.

It does not say that macOS booted or that any observed difference is an Apple compatibility requirement.

## Patch policy

P4.02 adds no Inferno source patch.

The compatibility patch chain still ends at `0005-arm-vmapple-feature-contract.patch`.

## Testing rule

`prepare-p4.02.sh` performs development-side static validation and persistent logging only.

The real P4.02 TCG capture is intentionally deferred to final integrated testing with the user's local QEMU and Apple guest inputs.

No manual per-objective runtime test is requested.
